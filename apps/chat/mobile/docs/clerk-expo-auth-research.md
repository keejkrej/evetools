# Clerk Expo hosted-auth review

Reviewed 2026-08-15 against `@clerk/expo` 4.3.0, Expo SDK 57, and the
current Evechat mobile and web sources. Only first-party Clerk and Expo
documentation and Clerk's official source repository were used.

## Verdict

The in-repo implementation is structurally correct: hosted auth is invoked
through Clerk's Expo SDK, the session cache uses SecureStore, the required
native config plugins and application identifiers are present, every protected
API request gets a current Clerk session token, and the Next.js API checks both
authentication and the configured owner ID.

Production readiness still depends on Clerk Dashboard state that cannot be
verified from the repository. The in-repo findings from this review have been
addressed: the setup guide now includes the iOS Team ID and Android namespace,
the mobile launcher uses a package-local public-only environment, and the app
normalizes its API URL while requiring HTTPS outside development.

## Requirement-by-requirement findings

### Hosted authentication: correct

[App.tsx](../App.tsx) imports `useHostedAuth` from
`@clerk/expo/hosted-auth` and calls `startHostedAuth({ mode: "sign-in" })`
inside the `ClerkProvider` tree. This is the API and import path documented by
Clerk. The SDK activates the resulting session itself and updates `useAuth()`;
the application does not need to call `setActive()` separately. A user closing
the browser is also handled safely: Clerk resolves with a null
`createdSessionId`, while authentication failures throw. The current UI treats
a dismissal as a quiet no-op, which is valid, though it could show a distinct
cancellation message if desired. See Clerk's
[hosted-auth guide](https://clerk.com/docs/guides/account-portal/hosted-auth)
and [`useHostedAuth()` reference](https://clerk.com/docs/reference/expo/native-hooks/use-hosted-auth).

[package.json](../package.json) includes all hosted-auth peer dependencies:
`expo-auth-session`, `expo-crypto`, and `expo-web-browser`. The installed
versions match Expo SDK 57 (`~57.0.7`, `~57.0.1`, and `~57.0.2` respectively),
as shown in the versioned Expo references for
[AuthSession](https://docs.expo.dev/versions/v57.0.0/sdk/auth-session/),
[Crypto](https://docs.expo.dev/versions/v57.0.0/sdk/crypto/), and
[WebBrowser](https://docs.expo.dev/versions/v57.0.0/sdk/webbrowser/).

### Provider and persisted session cache: correct

[App.tsx](../App.tsx) passes the explicit publishable key and `tokenCache` from
`@clerk/expo/token-cache` to `ClerkProvider`. That is Clerk's recommended Core
3 setup. The official token-cache implementation stores, reads, and deletes
tokens through `expo-secure-store`; see Expo's
[Clerk setup guide](https://docs.expo.dev/guides/using-clerk/) and the
[`@clerk/expo` 4.3.0 token-cache source](https://github.com/clerk/javascript/blob/e4302b7b513d280799f8f150fae366f80322bd64/packages/expo/src/token-cache/index.ts#L1-L53).

`expo-secure-store` `~57.0.1` is installed and its plugin appears in
[app.json](../app.json). Expo SDK 57 documents that SecureStore encrypts Android
values using the Android Keystore and stores iOS values in Keychain services;
it also requires its config plugin for native build-time configuration. See the
versioned [SecureStore reference](https://docs.expo.dev/versions/v57.0.0/sdk/securestore/).

### Native callback configuration: correct in source, Dashboard must be verified

[app.json](../app.json) contains both required plugins:

- `expo-secure-store`
- `@clerk/expo`

It also declares `ios.bundleIdentifier` and `android.package` as
`com.evechat.mobile`. Clerk documents that hosted auth derives its default
callback from those two fields and that the Clerk plugin registers the Android
intent filter. The exact callbacks generated by `@clerk/expo` 4.3.0 are:

- iOS: `com.evechat.mobile://callback`
- Android: `clerk://com.evechat.mobile.hosted-callback`

Those values come directly from Clerk's
[`useHostedAuth` 4.3.0 source](https://github.com/clerk/javascript/blob/e4302b7b513d280799f8f150fae366f80322bd64/packages/expo/src/hooks/useHostedAuth.ts#L210-L224),
and the Android intent filter is installed by Clerk's
[config plugin](https://github.com/clerk/javascript/blob/e4302b7b513d280799f8f150fae366f80322bd64/packages/expo/app.plugin.js#L26-L53).
The separate top-level Expo scheme, `eve`, does not override these defaults.

The repository cannot prove that Clerk Dashboard is configured. Before a
production build, enable the Native API and add the application under **Native
applications** using:

- iOS Bundle ID `com.evechat.mobile` **and the Apple Team ID**.
- Android package/namespace `com.evechat.mobile`.

Clerk says production instances validate callbacks against the registered
native application and that a production Expo application also needs a Clerk
domain. See Clerk's [Expo deployment guide](https://clerk.com/docs/guides/development/deployment/expo)
and [hosted-auth setup](https://clerk.com/docs/guides/account-portal/hosted-auth).
The [README](../README.md) includes both fields in its Dashboard checklist.

Changing either identifier or either plugin requires rebuilding the native
binary; an OTA JavaScript update is insufficient. This is consistent with
Expo SDK 57's [app-config reference](https://docs.expo.dev/versions/v57.0.0/config/app/)
and Clerk's hosted-auth instructions.

### Bearer authentication to the protected Next.js API: correct

[authenticated-fetch.ts](../src/authenticated-fetch.ts) calls Clerk's
`getToken()` for every request, refuses to send a request when no token is
available, and overwrites `Authorization` with `Bearer <session-token>` while
preserving other headers. The mobile app uses this wrapper for `/api/health`,
`/api/models`, and `/api/chat`. Clerk explicitly documents this pattern for
cross-origin/native clients in
[Making authenticated requests](https://clerk.com/docs/guides/development/making-requests)
and the Expo [`useAuth()` reference](https://clerk.com/docs/expo/reference/hooks/use-auth).

On the server, [proxy.ts](../../web/src/proxy.ts) runs `clerkMiddleware()` for
all API routes, and [owner-auth.ts](../../web/src/lib/owner-auth.ts) rejects a
missing Clerk user with 401 and a non-owner with 403. Clerk's `auth()` defaults
to accepting a `session_token`, which is the token returned by mobile
`getToken()`. The chat request guard deliberately accepts originless native
requests while rejecting a conflicting browser origin. See Clerk's
[`auth()` reference](https://clerk.com/docs/reference/nextjs/app-router/auth).

One defense-in-depth item remains: the server does not configure
`authorizedParties`. Clerk recommends constraining this value when verifying
requests to defend against subdomain-cookie leakage. Before adding it, record
the legitimate `azp` values produced by both the Evechat browser and Expo
sessions so the allowlist does not break one surface. See Clerk's
[`authenticateRequest()` guidance](https://clerk.com/docs/reference/backend/authenticate-request#authenticaterequestoptions)
and the
[`clerkMiddleware()` option](https://clerk.com/docs/reference/nextjs/clerk-middleware#clerkmiddleware-options).

### Public configuration and secret separation: correct

The mobile source statically reads only:

- `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY`
- `EXPO_PUBLIC_API_URL`

No Clerk secret key, owner ID, or gateway API key is referenced by mobile
code. Expo inlines statically referenced `EXPO_PUBLIC_*` values into the client
bundle and warns that every such value is public. Therefore the publishable key
and API URL belong there, while `CLERK_SECRET_KEY`, `EVE_OWNER_USER_ID`,
`OPENAI_BASE_URL`, and `OPENAI_API_KEY` must remain server-side. See Expo's current official
[environment-variable guide](https://docs.expo.dev/guides/environment-variables/)
and Expo's [Clerk setup guide](https://docs.expo.dev/guides/using-clerk/).

The [root package script](../../../../package.json) does not load the shared
server `.env` for `dev:chat-mobile`. Expo instead reads the package-local
`.env.local`, whose checked-in example contains only the two public variables.
EAS builds should likewise receive only those public values.

### Physical-device API URL: correct

The [README](../README.md) correctly warns that `localhost` on a physical phone
is the phone's own loopback interface, not the development computer. A phone
must use a deployed URL or an address reachable over the network; Expo's device
workflow likewise requires the computer and device to be on the same network
for LAN development. See Expo's [device development guide](https://docs.expo.dev/get-started/start-developing/).

For preview and production, `EXPO_PUBLIC_API_URL` must be an `https://` URL.
The implementation normalizes trailing slashes and rejects malformed,
credential-bearing, and non-HTTPS release URLs before a token can be sent.
Plain HTTP is accepted only under `__DEV__` for LAN development and may still
be blocked by Android: Expo SDK 57 documents Android 9+'s default
`usesCleartextTraffic: false`. See the versioned
[BuildProperties reference](https://docs.expo.dev/versions/v57.0.0/sdk/build-properties/#pluginconfigtypeandroid).

## Local verification performed

- `pnpm exec expo install --check` — dependencies are SDK-compatible.
- `pnpm typecheck` — passed.
- `pnpm test` — 6 authenticated-fetch and API URL tests passed.
- `pnpm exec expo config --type prebuild --json` — resolved both plugins and
  the expected bundle/package identifiers.

These checks do not replace a device-level sign-in test. Before release, run
hosted sign-in on one iOS and one Android production-style build, restart each
app to confirm SecureStore rehydration, call all three protected endpoints, and
verify that a valid non-owner session receives 403. That test is also the only
way to confirm the external Clerk Dashboard registration and deployed API URL.
